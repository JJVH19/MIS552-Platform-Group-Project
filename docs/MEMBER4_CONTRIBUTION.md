## 1. Feature Objective

The Event Coordination feature evaluates basketball
court booking proposals generated by the Chapter 5
Booking Assistant.

Three LLM agents represent athletes, event organizers
and facility managers. They exchange messages over
shared state and assess the suitability and feasibility
of a proposed booking.

The feature produces a recommendation rather than
independently confirming a reservation.

## 2. Stakeholder Responsibilities

| Agent | Stakeholder | Responsibility |
|---|---|---|
| Athlete Advisor | Basketball participants | Event suitability, skill level and participation concerns |
| Event Planner | Event organizers | Scheduling, event format, cost and operational readiness |
| Facility Coordinator | Facility managers | Availability, facility restrictions and booking conflicts |

## 3. Framework and Design Decisions

The implementation uses a custom Python orchestration
loop with OpenAI structured responses.

A custom loop was selected because it makes agent
routing, state transitions and hard execution limits
explicit and easier to inspect.

The trade-off is that state management, validation,
error handling and replay must be implemented manually
rather than provided by an agent framework.

The protocol permits four agent interactions within
a hard ceiling of six steps.

The Athlete Advisor receives a follow-up opportunity
after the Facility Coordinator evaluates the proposal.

## 4. Multi-Agent Communication

The communication sequence is:

1. Athlete Advisor to Event Planner.
2. Event Planner to Facility Coordinator.
3. Facility Coordinator to Athlete Advisor.
4. Athlete Advisor to Coordination Controller.

Each agent receives the booking proposal, marketplace
validation results and previous agent messages.

The final controller evaluates the agent decisions
and applies deterministic routing rules.

Possible outcomes include:

- blocked
- needs_review
- pending_approval
- execution_failed

Only eligible proposals may enter the approval queue.

## 5. Shared Data and Integration Contract

The feature reuses the team's existing synthetic data:

- data/events.json
- data/facilities.json
- data/availability.json
- data/bookings.json

The agreed entry point is:

    coordinate_booking(proposal: dict) -> dict

The required output fields remain:

- messages
- proposal
- approval_required
- status

Additional diagnostic fields support validation,
monitoring, execution limits and approval controls.

The feature does not modify the shared BookingProposal
schema in contracts.py.

## 7. Governance Controls

| Risk | Stakeholder | Potential harm | Mitigation | Status |
|---|---|---|---|---|
| Unsupported agent conclusions | Athletes and organizers | Suitable events may be unnecessarily blocked | Human review, preserved evidence and prompt evaluation | Implemented with limitations |
| Unauthorized booking authorization | Facility managers | Booking decisions made without consent | Explicit human acknowledgement and approval gate | Implemented |
| Stale availability or booking evidence | Organizers and facility managers | Conflicting reservations | Revalidation before approval and cached replay | Implemented |
| Incomplete agent execution | All stakeholders | Decisions based on incomplete assessment | Bounded protocol and fail-closed routing | Implemented |
| Untrusted instructions in marketplace data | All stakeholders | Attempted manipulation of agent behavior | Instruction hierarchy, data delimiters and deterministic approval controls | Partially implemented; adversarial testing pending |
| Duplicate or competing reservations | Facility managers | Multiple reservations for conflicting time periods | Existing booking ID and venue-level overlap validation | Implemented at validation stage; final commit control pending |

## 8. Human Review Boundary

Agents cannot grant final booking authorization.

Proposals with outstanding concerns require a human
to document the review before entering the final
approval queue.

An explicit approval action is required.

Blocked proposals cannot be overridden through the
approval controls.

The feature records authorization and rejection
decisions without writing a confirmed booking to
data/bookings.json.

The final mock booking function must be owned by
one agreed component and must revalidate availability
and prevent duplicate execution immediately before
writing the booking record.

## 9. Monitoring and Rollback Proposal

Recommended production metric:

Unsupported blocking rate.

Definition:

Number of BLOCK decisions overturned after documented
human review, divided by the number of reviewed BLOCK
decisions.

Proposed rollback condition:

If more than 10 percent of at least 30 reviewed BLOCK
decisions are found to lack supporting evidence,
disable automatic blocking recommendations and route
affected cases to manual assessment until the issue
is investigated.

This is a proposed production monitoring policy.
It is not a deployed monitoring service or an
empirically calibrated threshold.

## 10. Observed Results

Scenario 1: Intermediate Half-Court Challenge.

The original three-message live execution produced
three BLOCK decisions despite a valid availability
check. The facility was described as suitable for
small 3v3 tournaments, while the event specified 5v5.

The absence of an explicit prohibition makes the
blocking conclusion questionable.

Scenario 2: Saturday Basketball Social 3.

The complete four-message live protocol produced
four REVIEW decisions.

The requested slot was available and the estimated
rental cost was $165.

The feature correctly withheld automatic approval.
The proposal required additional human assessment.

These results show that availability and operational
readiness are distinct conditions.

## 11. Failure Analysis

The first scenario revealed possible excessive
blocking and unsupported inference.

A controlled prompt iteration instructed the agents
to distinguish uncertainty from explicit restrictions
and independently evaluate previous messages.

The Event Planner changed from BLOCK to REVIEW.
The other two agents retained BLOCK decisions.

The revision therefore demonstrated partial
improvement, rather than a complete resolution.

A future mitigation is to use explicit facility
capability fields and deterministic eligibility
rules instead of relying on marketing descriptions.

The agent trace remains available for human review.

## 12. Cached Demonstration

Cached mode replays recorded live model responses
for the supported booking proposal BOOK-002.

It checks the proposal and current marketplace
evidence against the original recorded run.

The same final decision rules and approval controls
remain active during replay.

No API key or new model request is required.

Unrelated proposals and stale recorded evidence are
rejected rather than assigned unrelated AI outputs.
